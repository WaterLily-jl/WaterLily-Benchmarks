# MPI scaling

[`mpi/`](https://github.com/WaterLily-jl/WaterLily-Benchmarks/tree/main/mpi) benchmarks the MPI extension of WaterLily (branch [`mpi-igg`](https://github.com/WaterLily-jl/WaterLily.jl/pull/281), on top of [ImplicitGlobalGrid.jl](https://github.com/eth-cscs/ImplicitGlobalGrid.jl)) on CPUs and GPUs: strong and weak scaling, and correctness checks against a run without MPI. It is separate from `benchmark.sh`: each run is one MPI launch of `mpi/scaling.jl`, which prints one line per run instead of writing JSON files.

| File | What it does |
|---|---|
| `mpi/setup.jl` | builds the `mpi/` environment (or another one, `--env`): WaterLily from `$WATERLILY_DIR`, MPI.jl bound to the system MPI, the WaterLily backend |
| `mpi/scaling.jl` | times `sim_step!` of a case on every rank and prints the time per step; `--check` also records global diagnostics |
| `mpi/check.jl` | compares the diagnostics of several runs with a reference run |
| `mpi/commit.jl` | `commit(dir)`, the commit of a clone through Julia's libgit2 (the compute nodes of JUPITER have no `git` once the jobs have purged the modules), which `scaling.jl` and the jobs print |
| `mpi/cuda_mpi_test.jl` | checks the CUDA-aware MPI alone: correctness on device buffers, and the ping-pong speed of device against host buffers (the sizes in `PINGPONG_BYTES`; profile it with Nsight Systems to see how MPI moves device buffers) |
| `mpi/halo_profile.jl` | profiles ImplicitGlobalGrid's `update_halo!` of WaterLily-sized device arrays alone: time per call, the CUDA calls and kernels behind it (`CUDA.@profile`), and where the host spends the time (Julia's profiler); optionally without CUDA.jl's implicit synchronization between streams, or with the routine of WaterLily's `face_comm!` (all split dimensions at once, as in the Poisson iterations since WaterLily `12c339c`) |
| `mpi/halo_trace.jl` | times each phase of ImplicitGlobalGrid's `update_halo!` (packing, posting, waiting, unpacking), per dimension and rank, next to the bare MPI exchange of the same faces from plain, page-locked and device buffers; needs the timers of the ImplicitGlobalGrid fork (branch [`halo-trace`](https://github.com/b-fg/ImplicitGlobalGrid.jl/tree/halo-trace)) and `IGG_TRACE=1`, which also make `scaling.jl` print the time per step spent in `update_halo!`, by array size; with `IGG_FUSED=1` or `2` (fork branch [`halo-fused`](https://github.com/b-fg/ImplicitGlobalGrid.jl/tree/halo-fused)) the fused halo updates of CUDA arrays instead, and the updates split by `update_halo_start!` and `update_halo_finish!` (WaterLily branch `mpi-igg-overlap`, which overlaps the Poisson halos with their stencil loops; A/B in `mpi/jobs/jupiter_overlap_ab.sh`) under signatures of their own |
| `mpi/plot_strong.jl`, `mpi/plot_weak.jl` | plot the scaling curves from the job outputs (with the `plotting` environment) |
| `mpi/jobs/` | the environment and job scripts of each cluster (`jupiter_*`, `snellius_*`) and `submit.sh` |
| `mpi/fused/` | the environment of WaterLily branch `mpi-igg-fused` (its own halos, without ImplicitGlobalGrid) and its jobs, `mpi/fused/jobs/` |

## Setup

On a login node (it needs internet), with a WaterLily.jl clone on branch `mpi-igg`:

```sh
source mpi/jobs/jupiter_env.sh                                # the modules of the jobs, and WATERLILY_DIR
julia mpi/setup.jl --cuda-local                               # GPUs: KernelAbstractions backend, CUDA.jl on the CUDA module
julia mpi/setup.jl --env=mpi/cpu --backend=SIMD --cuda-local  # CPUs, one thread per rank: a second environment
WATERLILY_DIR=$WATERLILY_DIR-fused julia mpi/setup.jl --env=mpi/fused --cuda-local     # branch mpi-igg-fused
```

`jupiter_env.sh` expects Julia from juliaup in `PATH`, loads GCC, ParaStationMPI (or `$WATERLILY_MPI`, e.g. `OpenMPI`) and CUDA, sets `JULIA_CUDA_MEMORY_POOL=none` (CUDA-aware MPI cannot pass memory of CUDA.jl's pool, see the known issues of MPI.jl), and keeps `JULIA_DEPOT_PATH` and `WATERLILY_DIR` when they are set (by default both go under `$PROJECT/$USER`). On a CPU cluster use `julia mpi/setup.jl --backend=SIMD` (one thread per rank). `setup.jl` binds MPI.jl to the MPI library of the loaded module, so run it again whenever the modules change (the preferences go to `mpi/LocalPreferences.toml`, not tracked; Julia 1.12 and later also write the path of WaterLily into `mpi/Project.toml`, a local change not to commit); MPIPreferences does not recognise ParaStation MPI, so `setup.jl` gives it the MPICH ABI (`--mpi-abi` sets another). On a laptop without an MPI module, `--system-mpi=false` keeps MPI.jl's own MPICH. The smoke test that `setup.jl` prints ends with a run on 2 ranks: `mpiexec` on a laptop, `srun` in an allocation on a cluster (JUPITER's login nodes have no `mpiexec`). `--cuda-local` sets CUDA.jl's runtime preference before anything loads CUDA.jl: loaded with its own CUDA libraries first, CUDA.jl mixes them with those of the CUDA module. The backend preference is fixed per environment: GPU runs need `KernelAbstractions`, and `scaling.jl` stops otherwise. So the CPU runs on JUPITER, one thread per rank as on Snellius, have their own environment, `mpi/cpu` (not tracked), with the packages of `mpi/Project.toml` and the `SIMD` backend; `--cuda-local` there keeps CUDA.jl, which it also holds, on the libraries of the CUDA module. WaterLily branch `mpi-igg-fused` has its own environment too, `mpi/fused`, whose `Project.toml` (tracked, which `setup.jl` keeps) is that of `mpi/` without ImplicitGlobalGrid, built from a WaterLily.jl clone of its own (`$WATERLILY_DIR-fused` above, next to the clone of `mpi/`), so that the clone of `mpi/` keeps its branch and the jobs that use it.

## Running `scaling.jl`

```sh
julia --project=mpi mpi/scaling.jl --case=tgv --log2p=7                               # serial
mpiexec -n 4 julia --project=mpi mpi/scaling.jl --case=tgv --log2p=7                  # 4 CPU ranks
srun -n 8 julia --project=mpi mpi/scaling.jl --case=tgv --log2p=8 --backend=CuArray   # 8 GPUs
```

The cases are those of `src/cases.jl`: `tgv` is `tgv_periodic` (triply periodic, a `(2^p)^3` box) and `sphere` is the sphere with a convective exit (a `16D×6D×6D` box, `D = 2^p`). `--log2p` sets the global size; with `--weak` it is the size per rank, and the global grid grows with the number of ranks (each rank of the weak TGV holds one period). `--dims=a,b,c` gives the size in cells instead. Other options: `--backend=Array|CuArray`, `--T=Float32|Float64`, `--steps` and `--warmup` (timed and untimed steps), and `--serial` (no MPI, even under `srun`). Rank 0 prints

```
[ Info: MPI np=8  case=tgv  grid=256x256x256  local=128x128x128  100 steps  per_step=...ms  levels=7  mean_iters=1.0  cost=...ns/DOF/dt  backend=CuArray
```

after a header with the commits of WaterLily and of WaterLily-Benchmarks, the MPI library and the device of each rank. When every rank sees all the GPUs of its node, ImplicitGlobalGrid gives each node-local rank its own GPU; when the launcher binds one GPU per rank (Slurm `--gpus-per-task=1`, the default on JUPITER), each rank keeps the one it sees. Check in the header that the ranks of a node show different GPUs. To test the GPU code paths on a machine with one GPU, let several ranks share it: `CUDA_VISIBLE_DEVICES=0 mpiexec -n 2 ...` (the timings are then meaningless).

## Correctness of the multi-GPU TGV

`--check=k` records the global kinetic energy, enstrophy, `max|u|`, `max|p|`, time step and Poisson iterations every `k` steps, and `--out=file.csv` saves them. [`mpi/jobs/jupiter_tgv_check.sh`](https://github.com/WaterLily-jl/WaterLily-Benchmarks/tree/main/mpi/jobs/jupiter_tgv_check.sh) runs the TGV from its initial condition on one GPU without MPI and with MPI on 1, 4 and 8 GPUs (two nodes), on 8 GPUs with CUDA-aware halos, and on 8 CPU ranks, then compares them all with `mpi/check.jl`:

```sh
sbatch -A <budget> mpi/jobs/jupiter_tgv_check.sh 7 200 10   # log2p, steps, record every 10 steps
```

What to expect, from the same check of a `64^3` TGV over 100 steps on one laptop GPU shared by up to 4 ranks:

- MPI on one GPU is identical to the run without MPI (`identical` in the table), as on CPUs.
- CUDA-aware (`IGG_CUDAAWARE_MPI=1`) and host-staged (`=0`) halos give identical results: only the transport changes.
- With more ranks, the diagnostics differ slightly from the serial run (largest relative difference of the kinetic energy about `4e-4` on 2 and 4 ranks): the halo is one cell wide, so at the faces between ranks the convection term uses the one-sided form of the domain boundaries.
- GPU and CPU runs with the same decomposition differ by FP32 round-off (about `3e-5`).

The halos of the solver (velocity, pressure, multigrid levels) go through ImplicitGlobalGrid, which either passes device buffers to a CUDA-aware MPI (`IGG_CUDAAWARE_MPI=1`) or stages them through host memory (`=0`). `jupiter_env.sh` stages them: on the GH200 nodes the copy to the host is cheap, and with ParaStation MPI a `512^3` TGV took 64.5 against 75.2 ms per step on 4 GPUs and 41.7 against 79.8 ms on 8 GPUs of two nodes. On one node `mpi/halo_profile.jl` finds `update_halo!` slower with device buffers at every face size of that run (239 against 227 µs per call at the 530 KB faces of `512^3`, 542 against 152 µs at 134 KB, 212 against 136 µs at 9 KB), although MPI alone moves a 530 KB face between two GPUs of a node about 3 times faster from device buffers (`mpi/cuda_mpi_test.jl`). ImplicitGlobalGrid can also choose per direction (`IGG_CUDAAWARE_MPI_DIMX`, `_DIMY`, `_DIMZ`), but do not stage x while passing another direction as device buffers: ImplicitGlobalGrid 0.17.3 then never exchanges the x halos. With x and y on device buffers and z, the direction across the nodes (`srun --distribution=cyclic`), staged, 8 GPUs took 63.7 against 51.2 ms. `ForwardDiff.Dual` and `Bool` arrays, which ImplicitGlobalGrid does not take, go through WaterLily's own `MPI.Sendrecv!` on device buffers, so they need a CUDA-aware MPI either way.

WaterLily branch `mpi-igg-fused` exchanges the halos itself, without ImplicitGlobalGrid: one message per neighbour rank (the diagonal ones included), packed and unpacked by one kernel each, for every array (velocity, pressure, multigrid levels, `Dual`, `Bool`), and the large Poisson, divergence and velocity-correction loops run on the cells that read no ghost while the messages travel (loops of at least `WATERLILY_OVERLAP_MIN` cells, default `2^20`). Its GPU halos are staged through page-locked host memory mapped into the device, unless `WATERLILY_GPU_AWARE_MPI` is `1` (every halo device to device, CUDA-aware MPI) or `N > 1` (the halos of at least `N` bytes); `mpi/fused/jobs/jupiter_fused_ab.sh` times these settings and checks that they give identical runs (`--project=mpi/fused`, results in `mpi/fused/data/`, not tracked). On 8 GPUs of 2 nodes the TGV 512³ took 47.6 ms per step there, against 32.9 ms with the ImplicitGlobalGrid fork's fused halos (on one node, 57.5 against 56.4 ms). `mpi/fused/jobs/jupiter_fused_diag.sh` runs both in one allocation, on 8 GPUs and on 4 (`mpi/fused/halo_diag.jl`, a wrapper of `scaling.jl`, times each phase of each halo with `DIAG_LAPS=1`, and stages through host buffers of the fork's kind with `DIAG_BUFFERS=register`). Its first run kept the gap (47.0 against 33.7 and 32.5 ms), also with the fork's buffers (47.2), and showed the host waiting for the pack and unpack kernels: they searched the halo regions per element, 3 ms for a 258³ halo of the 26 regions of 2×2×2 ranks on a laptop GPU, against 13 µs with the index of each element precomputed (WaterLily f38c69a). With that fix the same runs gave 31.8 ms on 8 GPUs, against the fork's 33.5 and 32.8, and a later run 32.4 (32.9 without the overlap, 37.0 device to device) against 34.4 and 33.7, and 54.9 against 56.9 ms on 4 GPUs. With the fix, device to device does not pay (`jupiter_fused_ab.sh`, job 2583225, every check identical): on 4 GPUs staged 55.7, device to device 56.6, from 1 MiB 54.3 ms; on 8 GPUs of 2 nodes 32.1, 37.0 and 33.5 ms. Its scaling curves (staged, `WATERLILY_ENV=mpi/fused`, `data/mpi/jupiter_*_fused/`, jobs 2590520-47) match those of the fork, run two days before in other allocations: TGV 512³ 31.9 against 33.5 ms per step on 8 GPUs and 15.6 against 16.4 on 64, 1024³ 36.2 against 37.8 on 64 and 22.0 against 22.3 on 256, 256³ per GPU 36.4 against 39.1 on 64 GPUs and 39.6 against 39.6 on 256 (stock ImplicitGlobalGrid: 49.2, 31.2 and 53.6 ms). Its 41.7 ms on 128 GPUs, above the 256-GPU time, was that job's allocation, as the fork's first 45.5 ms on 256 GPUs was (39.6 in an allocation with 128 GPUs at 38.0 and 38.3). `mpi/fused/jobs/jupiter_fused_scaling_ab.sh` runs the points on 128 and 256 GPUs (weak 256³ per GPU, strong 512³ and 1024³) of ImplicitGlobalGrid's own halos, the fork's and the branch's, in one allocation of 64 nodes. Its first run (job 2595500, WaterLily f38c69a for the branch and 74b5ff4 for the other two, `mpi/fused/data/scaling_ab_2595500/`) gave, in ms per step for ImplicitGlobalGrid's halos, the fork's and the branch's: weak 256³ per GPU 53.4, 38.3 and 37.1 on 128 GPUs, 54.6, 39.1 and 37.7 on 256, and 52.4, 38.2 and 37.5 on 128 again; strong 512³ on 128 GPUs 27.3, 12.5 and 15.4; 1024³ 41.4, 26.9 and 27.7 on 128 GPUs, and 36.7, 22.1 and 18.9 on 256. So the branch's weak curve is flat from 64 GPUs (36.4 ms) to 256 (37.7), and 2 to 3 % below the fork's at 128 and 256 GPUs. The repeat on 128 GPUs agrees within 1.2 %, but the strong points, one run each of 12 to 28 ms per step, scatter more: against the curves the fork gained 21 % at 512³ on 128 GPUs (15.9 ms there) and the branch 14 % at 1024³ on 256 (22.0 there), so this run does not settle the branch against the fork at those two points; a repeat would. The script takes the points (`POINTS`), the number of rounds of all of them (`ROUNDS`), the branch from any environment `mpi/fused*` and a variant with variables set (`fused:WATERLILY_OVERLAP_MIN=1099511627776`, the branch without the overlap); the repeat runs both points three times in turn with the fork, the branch at f38c69a and at d843529, and f38c69a without the overlap (at 512³ on 128 GPUs a rank's block, 64×128×128, is exactly the overlap's floor of 2²⁰ cells, so both overlap there, the branch at 6 sites and the fork at 4). Both send one message per neighbour rank, the diagonal ones included, in the Poisson iterations (the fork with `IGG_FUSED=2`), so the number of messages does not tell them apart. ImplicitGlobalGrid's own halos on 1024³ (`WATERLILY_TAG=stock IGG_FUSED=0`, WaterLily 74b5ff4 with the fork not fusing, which stands for stock ImplicitGlobalGrid: 50.0 against 49.2 ms on 8 GPUs at 512³; `data/mpi/jupiter_strong_tgv_10_stock/`, jobs 2595502-06) took 719.6, 376.6, 215.1, 122.3, 77.3 and 52.1 ms per step on 2 to 64 GPUs (one GPU runs out of memory), against the branch's 712.6, 362.6, 187.0, 104.6, 59.5 and 36.2: from -1 % on 2 GPUs to -30 % on 64, and -33 and -49 % on 128 and 256 in the allocation above. `mpi/fused/jobs/jupiter_fused_nsys.sh` traces both transports with Nsight Systems, to see what the MPI library does with a device buffer: the ping-pong of `mpi/cuda_mpi_test.jl` inside a node and between two, and the TGV with every halo and its phases marked (`halo_diag.jl`, `DIAG_NVTX=1`) on one rank of each node (`mpi/fused/jobs/nsys_ranks.sh`); `mpi/fused/nsys_halos.py` reads the SQLite exports and prints, per halo array and phase or per ping-pong size, the time and the CUDA API calls and memory copies made in it. Its first run (job 2594773, `mpi/fused/data/nsys_2594773/`, WaterLily f38c69a) refutes the explanation it was written to test: with device buffers the MPI library makes two CUDA API calls per message (`cuStreamIsCapturing` and `cuCtxGetCurrent`, about 0.1 µs) and copies nothing through CUDA, except within a node from 134 400 bytes (`cuda_ipc`: one `cuMemcpyDtoDAsync` over NVLink, then the polling of an event). The cost is the protocol UCX picks, which `UCX_PROTO_INFO=y` prints: for device memory it takes the zero-copy rendezvous only from 134 400 bytes within a node and from 656 796 bytes between nodes (for host memory from 13 537 and 25 203), and below that it copies the message into and out of its own buffers without a CUDA call (the Grace CPU can address the GPU's memory directly, which would explain it). One-way times of the ping-pong, device against host: 32 KB 13.0 against 7.1 µs within a node, 256 KB 55.3 against 17.9 µs between nodes; above the thresholds the same between nodes (1 MB 51.0 against 49.8 µs, the network card reading the GPU's memory) and faster within (1 MB 24.0 against 57.5 µs). In the TGV 512³ on 8 GPUs of 2 nodes a message carries both faces toward a periodic neighbour: 1.6 MB for the velocity, above both thresholds, 524 KB for the fine pressure, above the one within a node only, 131 KB on the 130³ level and at most 32 KB below it, under both. So on rank 0 the velocity halos are faster device to device (the wait for the messages 176 against 249 µs per call) and the pressure halos slower (225 against 124 µs on the fine level, 251 against 44 µs on the 130³ level, 1.4 to 2.9 times as long on the coarser ones, and 8 µs more to post the 14 messages): 13.8 against 9.2 ms per step for the pressure halos and 14.9 against 15.5 for the velocity ones, +3.9 ms in all against the +4.9 of job 2583225 (5 steps under the profiler). That is also why the halos of at least 1 MiB device to device paid on one node (their messages, above 134 400 bytes, go over NVLink) and not on two (the fine pressure's 524 KB messages between the nodes are under 656 796). Staged, a halo of 66³ or below takes 60 to 75 µs on rank 0 under the profiler, of which the host spends 15 and 18 µs launching the pack and the unpack kernel (5 to 6.5 µs of each in `cuLaunchKernelEx`) and 15 to 28 µs waiting for the messages. The traces with every CUDA API call (`*_all`) were imported only in part (nsys: wrong event order), so their counts are incomplete. `mpi/fused/jobs/jupiter_fused_ucx.sh` (2 nodes) lowers the size from which UCX takes the rendezvous for every memory type (`UCX_RNDV_THRESH`, by default 16384 and 65536; every message of the ping-pong, up to 64 MB, went through UCX's tag send, so the variable applies): the ping-pong at the sizes of the TGV's messages (`PINGPONG_BYTES`) within a node and between two, with the protocol tables summarized; TGV 512³ on 8 GPUs staged, device to device, and device to device from halos of 1 MiB and 256 KiB, at the default and each threshold (the times compare within the job: `mpi/fused` is at d843529 since 2026-10-31); and the time of each halo by array size, staged and device to device, from which to pick `WATERLILY_GPU_AWARE_MPI`. `mpi/fused/jobs/jupiter_fused_mg_ab.sh` times the branch's pressure solver with fewer halos and collectives (WaterLily d843529, bit-identical: no residual update, and so no halo, after the smoothing of the coarse levels, whose residual `restrict!` overwrites; no halo of the pressure before the first residual of a solve, whose ghosts the previous solve left in place; the solved cells counted once per update, and L₁ and L∞ in one collective; on 8 GPUs 64 pressure halos per step become 48, and 7 collectives per solve 4) against f38c69a in one allocation, on 8 GPUs and on 4, each from an environment of its own (`BASE` and `NEW`, built from clones at those commits as its header says, so that jobs still waiting in the queue keep the commit of `mpi/fused`). `IGG_CUDAAWARE_MPI`, `IGG_FUSED` and `IGG_TRACE` do not apply to it, and `mpi/halo_profile.jl` and `mpi/halo_trace.jl` time ImplicitGlobalGrid's halos only. Like ImplicitGlobalGrid's `select_device`, it gives each rank of a node its own GPU and stops when a node has more ranks than GPUs, unless the launcher binds one GPU per rank (one device in `CUDA_VISIBLE_DEVICES`, as with Slurm's `--gpus-per-task=1`).

## Scaling curves

`mpi/jobs/submit.sh` submits one job per node count, each running `mpi/jobs/<cluster>_scaling.sh`:

```sh
bash mpi/jobs/submit.sh jupiter strong tgv 9 "1 2 4 8 16" -- -A <budget>
bash mpi/jobs/submit.sh jupiter weak tgv 8 "1 2 4 8 16 32" -- -A <budget>
bash mpi/jobs/submit.sh jupiter_cpu strong tgv 8 "1 2 4 8 16" -- -A <budget>
bash mpi/jobs/submit.sh snellius weak tgv 6 "1 2 4 8"
```

`WATERLILY_ENV` sets the Julia environment of the runs (by default `mpi`, and `mpi/cpu` for `jupiter_cpu`), and the outputs then go to a directory named after it: `WATERLILY_ENV=mpi/fused bash mpi/jobs/submit.sh jupiter weak tgv 8 "1 2 4 8 16 32" -- -A <budget>` runs WaterLily branch `mpi-igg-fused` and writes to `data/mpi/jupiter_weak_tgv_8_fused/`. `WATERLILY_TAG` names the directory instead: `WATERLILY_TAG=stock IGG_FUSED=0 bash mpi/jobs/submit.sh jupiter strong tgv 10 "1 2 4 8 16" -- -A <budget>` runs ImplicitGlobalGrid's own halos in `mpi/` (the fork does not fuse them with `IGG_FUSED=0`) and writes to `data/mpi/jupiter_strong_tgv_10_stock/`. The job on one node also runs the points inside it (on JUPITER 1, 2 and 4 GPUs, the first without MPI, which is the reference of the efficiency); the others run one point each, so a point that failed can be submitted again alone (`... weak tgv 6 "32" -- -A <budget>`). Each GPU job prints the cores of the ranks of its first node, which should be those of one Grace CPU each (0-71, 72-143, ...). The outputs go to `data/mpi/<cluster>_<mode>_<case>_<log2p>/`, and the plot scripts read a whole directory and save the figure in it:

```sh
julia --project=plotting mpi/plot_strong.jl data/mpi/jupiter_strong_tgv_9
julia --project=plotting mpi/plot_weak.jl data/mpi/jupiter_weak_tgv_8 --refnp=4   # efficiency against one full node
```

On Snellius, `WATERLILY_RPN` sets the ranks per node (default 64), spread evenly over the CCXs of each node. On JUPITER there is one rank per GPU, 4 per node. `jupiter_cpu` runs `mpi/jobs/jupiter_cpu_scaling.sh` on the CPUs of the JUPITER nodes (4 Grace CPUs of 72 cores): one thread per rank, `WATERLILY_RPN` ranks per node (default 256, which splits the `2^p` grids, unlike all 288 cores), the same number on each Grace CPU, spread evenly over its cores. The job prints the NUMA nodes of the first node, to check that the cores of each Grace CPU are numbered as the binding assumes.

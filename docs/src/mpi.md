# MPI scaling

[`mpi/`](https://github.com/WaterLily-jl/WaterLily-Benchmarks/tree/main/mpi) benchmarks the MPI extension of WaterLily (branch [`mpi-igg`](https://github.com/WaterLily-jl/WaterLily.jl/pull/281); since `57443f8` it exchanges the halos itself, with [ImplicitGlobalGrid.jl](https://github.com/eth-cscs/ImplicitGlobalGrid.jl) as an optional backend, `WATERLILY_HALO=igg`, and up to `12c339c` ImplicitGlobalGrid carried them) on CPUs and GPUs: strong and weak scaling, and correctness checks against a run without MPI. It is separate from `benchmark.sh`: each run is one MPI launch of `mpi/scaling.jl`, which prints one line per run instead of writing JSON files.

| File | What it does |
|---|---|
| `mpi/setup.jl` | builds the `mpi/` environment (or another one, `--env`): WaterLily from `$WATERLILY_DIR`, MPI.jl bound to the system MPI, the WaterLily backend |
| `mpi/scaling.jl` | times `sim_step!` of a case on every rank and prints the time per step and the memory per cell; `--check` also records global diagnostics, `--partials` runs `ForwardDiff.Dual` numbers, `--laps` times the phases of WaterLily's halo exchange |
| `mpi/check.jl` | compares the diagnostics of several runs with a reference run, and the derivatives of an AD run with finite differences (`--fd`) |
| `mpi/collect.jl` | one CSV row per run from the outputs of `scaling.jl` (a job's directory of them, or several) |
| `mpi/cuda_mpi_test.jl` | checks the CUDA-aware MPI alone: correctness on device buffers, and the ping-pong speed of device against host buffers (the sizes in `PINGPONG_BYTES`; profile it with Nsight Systems to see how MPI moves device buffers) |
| `mpi/halo_profile.jl` | profiles ImplicitGlobalGrid's `update_halo!` of WaterLily-sized device arrays alone: time per call, the CUDA calls and kernels behind it (`CUDA.@profile`), and where the host spends the time (Julia's profiler); optionally without CUDA.jl's implicit synchronization between streams, or with the routine of WaterLily's `face_comm!` (all split dimensions at once, as in the Poisson iterations of WaterLily `12c339c`, the last whose halos were ImplicitGlobalGrid's; `CONCURRENT=1` needs that WaterLily) |
| `mpi/halo_trace.jl` | times each phase of ImplicitGlobalGrid's `update_halo!` (packing, posting, waiting, unpacking), per dimension and rank, next to the bare MPI exchange of the same faces from plain, page-locked and device buffers; needs the timers of the ImplicitGlobalGrid fork (branch [`halo-trace`](https://github.com/b-fg/ImplicitGlobalGrid.jl/tree/halo-trace)) and `IGG_TRACE=1`, which also make `scaling.jl` print the time per step spent in `update_halo!`, by array size; with `IGG_FUSED=1` or `2` (fork branch [`halo-fused`](https://github.com/b-fg/ImplicitGlobalGrid.jl/tree/halo-fused)) the fused halo updates of CUDA arrays instead, and the updates split by `update_halo_start!` and `update_halo_finish!` (WaterLily branch `mpi-igg-overlap`, which overlaps the Poisson halos with their stencil loops; A/B in `mpi/jobs/jupiter_overlap_ab.sh`) under signatures of their own |
| `mpi/plot_strong.jl`, `mpi/plot_weak.jl` | plot the scaling curves from the job outputs (with the `plotting` environment) |
| `mpi/jobs/` | the environment and job scripts of each cluster (`jupiter_*`, `snellius_*`) and `submit.sh`; `jupiter_ad.sh` and `jupiter_ad_check.sh` are the forward-mode AD runs |
| `mpi/fused/` | the environment of WaterLily branch `mpi-igg-fused` (its own halos, without ImplicitGlobalGrid) and its jobs, `mpi/fused/jobs/`; the branch is merged into `mpi-igg` (`57443f8`), so new runs use `mpi/` and this environment repeats the records |

## Setup

On a login node (it needs internet), with a WaterLily.jl clone on branch `mpi-igg`:

```sh
source mpi/jobs/jupiter_env.sh                                # the modules of the jobs, and WATERLILY_DIR
julia mpi/setup.jl --cuda-local                               # GPUs: KernelAbstractions backend, CUDA.jl on the CUDA module
julia mpi/setup.jl --env=mpi/cpu --backend=SIMD --cuda-local  # CPUs, one thread per rank: a second environment
WATERLILY_DIR=$WATERLILY_DIR-fused julia mpi/setup.jl --env=mpi/fused --cuda-local     # branch mpi-igg-fused (the records)
```

`jupiter_env.sh` expects Julia from juliaup in `PATH`, loads GCC, ParaStationMPI (or `$WATERLILY_MPI`, e.g. `OpenMPI`), CUDA and, inside a job, git (the compute nodes have no git of their own, and the jobs print the commit of each environment; on a login node the module's libcurl would break Julia's downloads in `setup.jl`), sets `JULIA_CUDA_MEMORY_POOL=none` (CUDA-aware MPI cannot pass memory of CUDA.jl's pool, see the known issues of MPI.jl), and keeps `JULIA_DEPOT_PATH` and `WATERLILY_DIR` when they are set (by default both go next to the clone of WaterLily-Benchmarks, in the project file system, and the clones of branch `mpi-igg-fused` are named after `$WATERLILY_DIR`). On a CPU cluster use `julia mpi/setup.jl --backend=SIMD` (one thread per rank). `setup.jl` binds MPI.jl to the MPI library of the loaded module, so run it again whenever the modules change (the preferences go to `mpi/LocalPreferences.toml`, not tracked; Julia 1.12 and later also write the path of WaterLily into `mpi/Project.toml`, a local change not to commit); MPIPreferences does not recognise ParaStation MPI, so `setup.jl` gives it the MPICH ABI (`--mpi-abi` sets another). `mpi/Project.toml` asks for CUDA.jl 6.5, which needs KernelAbstractions 0.10, the version of the WaterLily v1.11 runs; an environment resolved earlier moves to them when `setup.jl` runs again. On a laptop without an MPI module, `--system-mpi=false` keeps MPI.jl's own MPICH. The smoke test that `setup.jl` prints ends with a run on 2 ranks: `mpiexec` on a laptop, `srun` in an allocation on a cluster (JUPITER's login nodes have no `mpiexec`). `--cuda-local` sets CUDA.jl's runtime preference before anything loads CUDA.jl: loaded with its own CUDA libraries first, CUDA.jl mixes them with those of the CUDA module. The backend preference is fixed per environment: GPU runs need `KernelAbstractions`, and `scaling.jl` stops otherwise. So the CPU runs on JUPITER, one thread per rank as on Snellius, have their own environment, `mpi/cpu` (not tracked), with the packages of `mpi/Project.toml` and the `SIMD` backend; `--cuda-local` there keeps CUDA.jl, which it also holds, on the libraries of the CUDA module. WaterLily branch `mpi-igg-fused` has its own environment too, `mpi/fused`, whose `Project.toml` (tracked, which `setup.jl` keeps) is that of `mpi/` without ImplicitGlobalGrid, built from a WaterLily.jl clone of its own (`$WATERLILY_DIR-fused` above, next to the clone of `mpi/`), so that the clone of `mpi/` keeps its branch and the jobs that use it. Since `mpi-igg` carries that exchange (`57443f8`), `mpi/` runs it by default and keeps ImplicitGlobalGrid for `WATERLILY_HALO=igg`; after moving the clone of `mpi/` to that commit, run `setup.jl` again (WaterLily v1.11 brings KernelAbstractions 0.10).

## Running `scaling.jl`

```sh
julia --project=mpi mpi/scaling.jl --case=tgv --log2p=7                               # serial
mpiexec -n 4 julia --project=mpi mpi/scaling.jl --case=tgv --log2p=7                  # 4 CPU ranks
srun -n 8 julia --project=mpi mpi/scaling.jl --case=tgv --log2p=8 --backend=CuArray   # 8 GPUs
```

The cases are those of `src/cases.jl`: `tgv` is `tgv_periodic` (triply periodic, a `(2^p)^3` box) and `sphere` is the sphere with a convective exit (a `16D×6D×6D` box, `D = 2^p`). `--log2p` sets the global size; with `--weak` it is the size per rank, and the global grid grows with the number of ranks (each rank of the weak TGV holds one period). `--dims=a,b,c` gives the size in cells instead. Other options: `--backend=Array|CuArray`, `--T=Float32|Float64`, `--partials=N` (`ForwardDiff.Dual` numbers, see [Forward-mode AD](@ref)), `--Re`, `--steps` and `--warmup` (timed and untimed steps), `--laps` (the halo timers, same section) and `--serial` (no MPI, even under `srun`). Rank 0 prints

```
[ Info: MPI np=8  case=tgv  grid=256x256x256  local=128x128x128  100 steps  per_step=...ms  levels=7  mean_iters=1.0  cost=...ns/DOF/dt  backend=CuArray  T=Float32  partials=0
[ Info: MEMORY  cells=2097152  arrays=...B/cell  halos=...B/cell  device=...MB  host_rss=...MB
```

(the second line is the memory of its block: the bytes of the arrays of the simulation, ghost cells included, and of the halo plans and buffers, both per interior cell, then the memory in use on its GPU, which includes the CUDA context and any other process, and the peak resident memory of its process)

after a header with the commits of WaterLily and of WaterLily-Benchmarks, the MPI library and the device of each rank. When every rank sees all the GPUs of its node, `init_waterlily_mpi` gives each node-local rank its own GPU (ImplicitGlobalGrid's `select_device` did up to WaterLily `12c339c`); when the launcher binds one GPU per rank (Slurm `--gpus-per-task=1`, the default on JUPITER), each rank keeps the one it sees. Check in the header that the ranks of a node show different GPUs. To test the GPU code paths on a machine with one GPU, let several ranks share it: `CUDA_VISIBLE_DEVICES=0 mpiexec -n 2 ...` (the timings are then meaningless).

## Correctness of the multi-GPU TGV

`--check=k` records the global kinetic energy, enstrophy, `max|u|`, `max|p|`, time step and Poisson iterations every `k` steps, and `--out=file.csv` saves them. [`mpi/jobs/jupiter_tgv_check.sh`](https://github.com/WaterLily-jl/WaterLily-Benchmarks/tree/main/mpi/jobs/jupiter_tgv_check.sh) runs the TGV from its initial condition on one GPU without MPI and with MPI on 1, 4 and 8 GPUs (two nodes), on 8 GPUs with CUDA-aware halos and with ImplicitGlobalGrid's halos (`WATERLILY_HALO=igg`), and on 8 CPU ranks, then compares them all with `mpi/check.jl`:

```sh
sbatch -A <budget> mpi/jobs/jupiter_tgv_check.sh 7 200 10   # log2p, steps, record every 10 steps
```

What to expect, from the same check of a `64^3` TGV over 100 steps on one laptop GPU shared by up to 4 ranks:

- MPI on one GPU is identical to the run without MPI (`identical` in the table), as on CPUs.
- CUDA-aware (`WATERLILY_GPU_AWARE_MPI=1`, or `IGG_CUDAAWARE_MPI=1` for ImplicitGlobalGrid's halos) and host-staged (`=0`) halos give identical results: only the transport changes. So do WaterLily's halos and ImplicitGlobalGrid's (`WATERLILY_HALO=igg`).
- With more ranks, the diagnostics differ slightly from the serial run (largest relative difference of the kinetic energy about `4e-4` on 2 and 4 ranks): the halo is one cell wide, so at the faces between ranks the convection term uses the one-sided form of the domain boundaries.
- GPU and CPU runs with the same decomposition differ by FP32 round-off (about `3e-5`).

On JUPITER (job 2772635, WaterLily `57443f8`, TGV `128^3` over 200 steps, 2 nodes, CUDA.jl 6.4.2 and KernelAbstractions 0.9) the same holds: MPI on one GPU is identical to the run without MPI; on 8 GPUs the CUDA-aware run and the one with ImplicitGlobalGrid's halos (`WATERLILY_HALO=igg`) are identical to the host-staged one; 4 and 8 GPUs differ from the serial run by at most `1.3e-5` in kinetic energy, `2.3e-4` in the time step and `8e-4` in `max|p|`; 8 GPUs and 8 CPU ranks by `2e-5` in kinetic energy. Its repeat on CUDA.jl 6.5.1 and KernelAbstractions 0.10.6 (job 2773171) gives the same: both halo backends and both transports identical on 8 GPUs, MPI on one GPU identical to serial, and the same differences against it to two digits. Its times per step are not timings: the check runs without warm-up, so they include the compilation.

Up to WaterLily `12c339c` (and with `WATERLILY_HALO=igg` since `57443f8`, for `Float32` and `Float64` arrays) the halos of the solver (velocity, pressure, multigrid levels) go through ImplicitGlobalGrid, which either passes device buffers to a CUDA-aware MPI (`IGG_CUDAAWARE_MPI=1`) or stages them through host memory (`=0`). `jupiter_env.sh` stages them: on the GH200 nodes the copy to the host is cheap, and with ParaStation MPI a `512^3` TGV took 64.5 against 75.2 ms per step on 4 GPUs and 41.7 against 79.8 ms on 8 GPUs of two nodes. On one node `mpi/halo_profile.jl` finds `update_halo!` slower with device buffers at every face size of that run (239 against 227 µs per call at the 530 KB faces of `512^3`, 542 against 152 µs at 134 KB, 212 against 136 µs at 9 KB), although MPI alone moves a 530 KB face between two GPUs of a node about 3 times faster from device buffers (`mpi/cuda_mpi_test.jl`). ImplicitGlobalGrid can also choose per direction (`IGG_CUDAAWARE_MPI_DIMX`, `_DIMY`, `_DIMZ`), but do not stage x while passing another direction as device buffers: ImplicitGlobalGrid 0.17.3 then never exchanges the x halos. With x and y on device buffers and z, the direction across the nodes (`srun --distribution=cyclic`), staged, 8 GPUs took 63.7 against 51.2 ms. `ForwardDiff.Dual` and `Bool` arrays, which ImplicitGlobalGrid does not take, go through WaterLily's own `MPI.Sendrecv!` on device buffers, so they need a CUDA-aware MPI either way.

WaterLily branch `mpi-igg-fused`, merged into `mpi-igg` at `57443f8`, exchanges the halos itself, without ImplicitGlobalGrid: one message per neighbour rank (the diagonal ones included), packed and unpacked by one kernel each, for every array (velocity, pressure, multigrid levels, `Dual`, `Bool`), and the large Poisson, divergence and velocity-correction loops run on the cells that read no ghost while the messages travel (loops of at least `WATERLILY_OVERLAP_MIN` cells, default `2^20`). Its GPU halos are staged through page-locked host memory mapped into the device, unless `WATERLILY_GPU_AWARE_MPI` is `1` (every halo device to device, CUDA-aware MPI) or `N > 1` (the halos of at least `N` bytes); `mpi/fused/jobs/jupiter_fused_ab.sh` times these settings and checks that they give identical runs (`--project=mpi/fused`, results in `mpi/fused/data/`, not tracked). On 8 GPUs of 2 nodes the TGV 512³ took 47.6 ms per step there, against 32.9 ms with the ImplicitGlobalGrid fork's fused halos (on one node, 57.5 against 56.4 ms). `mpi/fused/jobs/jupiter_fused_diag.sh` runs both in one allocation, on 8 GPUs and on 4 (`mpi/fused/halo_diag.jl`, a wrapper of `scaling.jl`, times each phase of each halo with `DIAG_LAPS=1`, and stages through host buffers of the fork's kind with `DIAG_BUFFERS=register`). Its first run kept the gap (47.0 against 33.7 and 32.5 ms), also with the fork's buffers (47.2), and showed the host waiting for the pack and unpack kernels: they searched the halo regions per element, 3 ms for a 258³ halo of the 26 regions of 2×2×2 ranks on a laptop GPU, against 13 µs with the index of each element precomputed (WaterLily f38c69a). With that fix the same runs gave 31.8 ms on 8 GPUs, against the fork's 33.5 and 32.8, and a later run 32.4 (32.9 without the overlap, 37.0 device to device) against 34.4 and 33.7, and 54.9 against 56.9 ms on 4 GPUs. With the fix, device to device does not pay (`jupiter_fused_ab.sh`, job 2583225, every check identical): on 4 GPUs staged 55.7, device to device 56.6, from 1 MiB 54.3 ms; on 8 GPUs of 2 nodes 32.1, 37.0 and 33.5 ms. Its scaling curves (staged, `WATERLILY_ENV=mpi/fused`, `data/mpi/jupiter_*_fused/`, jobs 2590520-47) match those of the fork, run two days before in other allocations: TGV 512³ 31.9 against 33.5 ms per step on 8 GPUs and 15.6 against 16.4 on 64, 1024³ 36.2 against 37.8 on 64 and 22.0 against 22.3 on 256, 256³ per GPU 36.4 against 39.1 on 64 GPUs and 39.6 against 39.6 on 256 (stock ImplicitGlobalGrid: 49.2, 31.2 and 53.6 ms). Its 41.7 ms on 128 GPUs, above the 256-GPU time, was that job's allocation, as the fork's first 45.5 ms on 256 GPUs was (39.6 in an allocation with 128 GPUs at 38.0 and 38.3). `mpi/fused/jobs/jupiter_fused_scaling_ab.sh` runs the points on 128 and 256 GPUs (weak 256³ per GPU, strong 512³ and 1024³) of ImplicitGlobalGrid's own halos, the fork's and the branch's, in one allocation of 64 nodes. Its first run (job 2595500, WaterLily f38c69a for the branch and 74b5ff4 for the other two, `mpi/fused/data/scaling_ab_2595500/`) gave, in ms per step for ImplicitGlobalGrid's halos, the fork's and the branch's: weak 256³ per GPU 53.4, 38.3 and 37.1 on 128 GPUs, 54.6, 39.1 and 37.7 on 256, and 52.4, 38.2 and 37.5 on 128 again; strong 512³ on 128 GPUs 27.3, 12.5 and 15.4; 1024³ 41.4, 26.9 and 27.7 on 128 GPUs, and 36.7, 22.1 and 18.9 on 256. So the branch's weak curve is flat from 64 GPUs (36.4 ms) to 256 (37.7), and 2 to 3 % below the fork's at 128 and 256 GPUs. The repeat on 128 GPUs agrees within 1.2 %, but the strong points, one run each of 12 to 28 ms per step, scatter more: against the curves the fork gained 21 % at 512³ on 128 GPUs (15.9 ms there) and the branch 14 % at 1024³ on 256 (22.0 there), so this run does not settle the branch against the fork at those two points. The script takes the points (`POINTS`), the number of rounds of all of them (`ROUNDS`), the branch from any environment `mpi/fused*` and a variant with variables set (`fused:WATERLILY_OVERLAP_MIN=1099511627776`, the branch without the overlap). Its repeat (job 2609753, `mpi/fused/data/scaling_ab_2609753/`) ran both points three times in turn with the fork, the branch from `mpi/fused-f38c69a` and from `mpi/fused`, and f38c69a without the overlap (at 512³ on 128 GPUs a rank's block, 64×128×128, is exactly the overlap's floor of 2²⁰ cells, so both overlap there, the branch at 6 sites and the fork at 4). d843529 had not reached the clone of `mpi/fused` on JUPITER, so both environments of the branch were at f38c69a: six runs of the same code, which give the spread within one allocation. They took 10.6 to 16.7 ms per step at 512³ on 128 GPUs, and once 25.9 (median 15.1), and 18.4 to 23.6 at 1024³ on 256 (median 20.6); the fork 13.2 to 15.5 (mean 14.4) and 22.6 to 24.6 (mean 23.4); the branch without the overlap 13.8 to 15.3 (14.6) and 18.5 to 22.0 (20.4). So at 512³ on 128 GPUs the fork and the branch take the same time (the fork's 12.5 of job 2595500 was a fast run, as the branch's 10.6 here), and at 1024³ on 256 the branch is about 11 % faster: five of its six runs are below every run of the fork, as in job 2595500 (18.9 against 22.1), while the curves, from other allocations, have them equal (22.0 against 22.3). The overlap gains nothing at either point, as on 8 GPUs. Every run has the same multigrid levels and mean iterations, and the fork runs first in every round. Both send one message per neighbour rank, the diagonal ones included, in the Poisson iterations (the fork with `IGG_FUSED=2`), so the number of messages does not tell them apart. ImplicitGlobalGrid's own halos on 1024³ (`WATERLILY_TAG=stock IGG_FUSED=0`, WaterLily 74b5ff4 with the fork not fusing, which stands for stock ImplicitGlobalGrid: 50.0 against 49.2 ms on 8 GPUs at 512³; `data/mpi/jupiter_strong_tgv_10_stock/`, jobs 2595502-06) took 719.6, 376.6, 215.1, 122.3, 77.3 and 52.1 ms per step on 2 to 64 GPUs (one GPU runs out of memory), against the branch's 712.6, 362.6, 187.0, 104.6, 59.5 and 36.2: from -1 % on 2 GPUs to -30 % on 64, and -33 and -49 % on 128 and 256 in the allocation above. `mpi/fused/jobs/jupiter_fused_nsys.sh` traces both transports with Nsight Systems, to see what the MPI library does with a device buffer: the ping-pong of `mpi/cuda_mpi_test.jl` inside a node and between two, and the TGV with every halo and its phases marked (`halo_diag.jl`, `DIAG_NVTX=1`) on one rank of each node (`mpi/fused/jobs/nsys_ranks.sh`); `mpi/fused/nsys_halos.py` reads the SQLite exports and prints, per halo array and phase or per ping-pong size, the time and the CUDA API calls and memory copies made in it. Its first run (job 2594773, `mpi/fused/data/nsys_2594773/`, WaterLily f38c69a) refutes the explanation it was written to test: with device buffers the MPI library makes two CUDA API calls per message (`cuStreamIsCapturing` and `cuCtxGetCurrent`, about 0.1 µs) and copies nothing through CUDA, except within a node from 134 400 bytes (`cuda_ipc`: one `cuMemcpyDtoDAsync` over NVLink, then the polling of an event). The cost is the protocol UCX picks, which `UCX_PROTO_INFO=y` prints: for device memory it takes the zero-copy rendezvous only from 134 400 bytes within a node and from 656 796 bytes between nodes (for host memory from 13 537 and 25 203), and below that it copies the message into and out of its own buffers without a CUDA call (the Grace CPU can address the GPU's memory directly, which would explain it). One-way times of the ping-pong, device against host: 32 KB 13.0 against 7.1 µs within a node, 256 KB 55.3 against 17.9 µs between nodes; above the thresholds the same between nodes (1 MB 51.0 against 49.8 µs, the network card reading the GPU's memory) and faster within (1 MB 24.0 against 57.5 µs). In the TGV 512³ on 8 GPUs of 2 nodes a message carries both faces toward a periodic neighbour: 1.6 MB for the velocity, above both thresholds, 524 KB for the fine pressure, above the one within a node only, 131 KB on the 130³ level and at most 32 KB below it, under both. So on rank 0 the velocity halos are faster device to device (the wait for the messages 176 against 249 µs per call) and the pressure halos slower (225 against 124 µs on the fine level, 251 against 44 µs on the 130³ level, 1.4 to 2.9 times as long on the coarser ones, and 8 µs more to post the 14 messages): 13.8 against 9.2 ms per step for the pressure halos and 14.9 against 15.5 for the velocity ones, +3.9 ms in all against the +4.9 of job 2583225 (5 steps under the profiler). That is also why the halos of at least 1 MiB device to device paid on one node (their messages, above 134 400 bytes, go over NVLink) and not on two (the fine pressure's 524 KB messages between the nodes are under 656 796). Staged, a halo of 66³ or below takes 60 to 75 µs on rank 0 under the profiler, of which the host spends 15 and 18 µs launching the pack and the unpack kernel (5 to 6.5 µs of each in `cuLaunchKernelEx`) and 15 to 28 µs waiting for the messages. Its first run (job 2609752, `mpi/fused/data/ucx_2609752/`, WaterLily f38c69a) moves the switch: with 16384 or 65536, device memory goes rendezvous from 16 or 64 KiB, within a node and between nodes (host memory too). Its time of each halo on 8 GPUs counts 68 halos per step before and 52 after (the pressure's 64 and 48), 25.7 and 23.8 ms per step: the fine pressure 4.85 and 4.41 ms (12 and 10 halos), the 130³ level 1.45 and 1.16, and the levels of 66³ and below 3.34 and 2.40 (44 and 32 halos of 70 to 85 µs), the velocity's 15.6 ms unchanged (most of it the host's wait for the momentum kernels before the halo). So the 2.0 ms the step gains on 8 GPUs are the 1.9 ms of the halos dropped and the collectives. Its scaling curves (jobs 2614113-32, `WATERLILY_ENV=mpi/fused WATERLILY_TAG=fused_d843529`, `data/mpi/jupiter_{strong_tgv_9,strong_tgv_10,weak_tgv_8}_fused_d843529/`, each point in its own allocation, as the f38c69a curves) take, in ms per step: TGV 512³ on 1 to 128 GPUs 167.9, 97.7, 52.9, 30.5, 20.4, 16.0, 13.3, 12.5 (f38c69a 170.6, 101.1, 54.7, 31.9, 23.4, 18.0, 15.6, 16.2: -2 to -23 %, and no longer slower on 128 GPUs than on 64), 1024³ on 2 to 256 GPUs 692.7, 355.1, 181.5, 101.1, 56.0, 33.5, 23.9, 21.0 (712.6, 362.6, 187.0, 104.6, 59.5, 36.2, 27.2, 22.0: -2 to -12 %; it does not fit on one GPU), and 256³ per GPU on 1 to 256 GPUs 24.2, 28.7, 29.0, 30.2, 31.5, 32.2, 33.3, 34.0, 35.4 (24.8, 30.4, 30.5, 32.4, 33.4, 34.6, 36.4, 41.7, 39.6: -2 to -11 %, and -18 % on 128 GPUs, where the f38c69a point was its allocation), a weak efficiency on 256 GPUs against one node of 82 % (77 %). The gain grows with the number of GPUs, as the halos it drops are the coarse levels' latency; the strong points beyond 64 GPUs scatter by up to a quarter between allocations (job 2609753), so their gains are single runs. `IGG_CUDAAWARE_MPI`, `IGG_FUSED` and `IGG_TRACE` do not apply to it, and `mpi/halo_profile.jl` and `mpi/halo_trace.jl` time ImplicitGlobalGrid's halos only. Like ImplicitGlobalGrid's `select_device`, it gives each rank of a node its own GPU and stops when a node has more ranks than GPUs, unless the launcher binds one GPU per rank (one device in `CUDA_VISIBLE_DEVICES`, as with Slurm's `--gpus-per-task=1`).

Since `57443f8` branch `mpi-igg` is that exchange plus halo backends: `init_waterlily_mpi(...; halo)` picks WaterLily's own (`native`, the default) or ImplicitGlobalGrid's (`igg`, with `using ImplicitGlobalGrid`, which `scaling.jl` loads under `WATERLILY_HALO=igg`), and the header of `scaling.jl` prints which (`halo=`). The `igg` backend exchanges `Float32` and `Float64` arrays with `update_halo!`, one dimension after the other, on one ImplicitGlobalGrid grid per array size built on WaterLily's Cartesian communicator; `Dual` and `Bool` arrays take WaterLily's exchange, and the loops of `comm!(f, ...)` run after the halo instead of during it. On a laptop the two backends give bit-identical runs (TGV on 8 CPU ranks and on 2 ranks of one GPU), and ImplicitGlobalGrid's halos are slower there as on JUPITER (TGV 64³ on 8 CPU ranks 22 to 24 against 17 ms per step).

## Scaling curves

`mpi/jobs/submit.sh` submits one job per node count, each running `mpi/jobs/<cluster>_scaling.sh`:

```sh
bash mpi/jobs/submit.sh jupiter strong tgv 9 "1 2 4 8 16" -- -A <budget>
bash mpi/jobs/submit.sh jupiter weak tgv 8 "1 2 4 8 16 32" -- -A <budget>
bash mpi/jobs/submit.sh jupiter_cpu strong tgv 8 "1 2 4 8 16" -- -A <budget>
bash mpi/jobs/submit.sh snellius weak tgv 6 "1 2 4 8"
```

`WATERLILY_ENV` sets the Julia environment of the runs (by default `mpi`, and `mpi/cpu` for `jupiter_cpu`), and the outputs then go to a directory named after it: `WATERLILY_ENV=mpi/fused bash mpi/jobs/submit.sh jupiter weak tgv 8 "1 2 4 8 16 32" -- -A <budget>` runs WaterLily branch `mpi-igg-fused` and writes to `data/mpi/jupiter_weak_tgv_8_fused/`. `WATERLILY_TAG` names the directory instead: `WATERLILY_TAG=stock IGG_FUSED=0 bash mpi/jobs/submit.sh jupiter strong tgv 10 "1 2 4 8 16" -- -A <budget>` ran ImplicitGlobalGrid's own halos in `mpi/` (WaterLily `74b5ff4`, the fork not fusing them with `IGG_FUSED=0`) and wrote to `data/mpi/jupiter_strong_tgv_10_stock/`; with WaterLily `57443f8` in `mpi/`, `WATERLILY_TAG=igg WATERLILY_HALO=igg` runs them through the `igg` backend. The job on one node also runs the points inside it (on JUPITER 1, 2 and 4 GPUs, the first without MPI, which is the reference of the efficiency); the others run one point each, so a point that failed can be submitted again alone (`... weak tgv 6 "32" -- -A <budget>`). Each GPU job prints the cores of the ranks of its first node, which should be those of one Grace CPU each (0-71, 72-143, ...). The outputs go to `data/mpi/<cluster>_<mode>_<case>_<log2p>/`, and the plot scripts read a whole directory and save the figure in it:

```sh
julia --project=plotting mpi/plot_strong.jl data/mpi/jupiter_strong_tgv_9
julia --project=plotting mpi/plot_weak.jl data/mpi/jupiter_weak_tgv_8 --refnp=4   # efficiency against one full node
julia --project=plotting mpi/plot_weak.jl data/mpi/jupiter_weak_tgv_8 --inset=4   # against one GPU, inset against one node
julia --project=plotting mpi/plot_strong.jl --combine --out=data/mpi/jupiter_strong_tgv_9_10.pdf data/mpi/jupiter_strong_tgv_9 data/mpi/jupiter_strong_tgv_10
```

`--combine` puts the curves of several directories in one figure, saved as `--out`. The colours are those of the ParCFD 2026 figures: one hue of `:lightrainbow` per case and size in the strong-scaling plots (TGV 512³ and 1024³ keep theirs from figure to figure), teal and red for the first two curves of a weak-scaling plot. The inset's x axis is log2 when its rank counts double, and linear for half-node steps.

On Snellius, `WATERLILY_RPN` sets the ranks per node (default 64), spread evenly over the CCXs of each node. On JUPITER there is one rank per GPU, 4 per node. `jupiter_cpu` runs `mpi/jobs/jupiter_cpu_scaling.sh` on the CPUs of the JUPITER nodes (4 Grace CPUs of 72 cores): one thread per rank, `WATERLILY_RPN` ranks per node (default 256, which splits the `2^p` grids, unlike all 288 cores), the same number on each Grace CPU, spread evenly over its cores. The job prints the NUMA nodes of the first node, to check that the cores of each Grace CPU are numbered as the binding assumes.

## Forward-mode AD

`--partials=N` runs the TGV with `ForwardDiff.Dual` numbers of `N` partials on top of `--T`, taken from WaterLily's own ForwardDiff, so the environment needs no package: partial 1 seeds the viscosity (d/dν), partial 2 the amplitude of the initial velocity (d/dU), and the others repeat d/dν (their cost and memory are what they are for). With `--check` the records also hold `nu` and the derivatives of the reduced diagnostics (`dKE_dnu`, `denstrophy_dnu`, `dumax_dnu`, `dpmax_dnu`, and `..._dU` from two partials on), which `mpi/check.jl` compares like the other columns, also between runs with different columns (the values of a run with partials against a run without). The functional is the diagnostic after a fixed number of time steps, whose sizes depend on ν through the CFL condition. `--Re` sets the Reynolds number (ν(1±ε) is `--Re=1600/(1±ε)`), and `--tol` and `--itmx` the tolerance and the largest number of iterations of the pressure solver (WaterLily's `poisson_kwargs`; by default its own `2e-3` and 32).

```sh
mpiexec -n 8 julia --project=mpi mpi/scaling.jl --log2p=6 --steps=50 --warmup=0 --check=10 --partials=1 --out=ad_np8.csv
julia mpi/check.jl ad_serial.csv ad_np8.csv                    # AD on 8 ranks against serial AD: largest and last difference
julia mpi/check.jl --fd ad64_np8.csv plus_np8.csv minus_np8.csv  # AD against (q₊ - q₋)/(ν₊ - ν₋) of two runs without partials
```

Three things decide what such a comparison shows (TGV `64^3` from its initial condition over 50 steps, a laminar horizon, on a laptop: serial and 1, 2, 4, 8 CPU ranks, WaterLily `43df5e6`, `SIMD` backend):

- **The pressure tolerance limits the derivative before anything else does.** The solver stops on the residual of the values and never looks at the partials, so with WaterLily's tolerance (`2e-3`, one V-cycle per solve here) `dKE_dnu` of the last record is 3.4 % from its converged value, while the kinetic energy is `9e-5` from its own. With `--tol=2e-4` (2 V-cycles) the derivative is `5.6e-3` away, with `2e-5` (3.3) `3.3e-3`, and from `2e-6` on (4.5) converged to the six digits printed in `Float64` (in `Float32` `1e-3` at `2e-6` and `9e-5` at `1e-7`, 6.3 V-cycles). This holds without MPI. The times per step of `Dual` against `Float32` at the default tolerance are therefore times of a derivative with that error; `--tol` times an accurate one.
- **AD against finite differences needs `Float64`, a converged pressure solve and a small step.** At the default tolerance the stopping test and the adaptive relaxation of the solver make the result jump with ν, which a difference sees and AD does not (`1e-3` between the two, serial). With `--tol=1e-9` the central difference of the serial run agrees with AD to `3e-7` at ε = `1e-5`, but to `1e-3` at ε = `1e-4`, whatever the tolerance: the scheme is piecewise smooth (the time step is a maximum over the cells, the QUICK limiter a median, and the one-sided fluxes at the rank faces switch with the sign of the velocity), and a difference across a kink averages two slopes. On 4 ranks the difference falls from `7e-4` (ε = `1e-4`) through `3e-4` and `2e-5` to `5e-7` (ε = `1e-7`), and `--tol=1e-12` changes none of it down to ε = `1e-6`; on 2 and 8 ranks it is `2e-5` at ε = `1e-5`. `check.jl --fd` warns when the Poisson iterations of the three runs differ.
- **AD on several ranks against serial AD also holds the decomposition.** MPI on one rank is identical to serial, partials included, and the values of a `Dual` run equal those of a `Float32` run within round-off (`8e-7`). With converged solves (`Float64`, `--tol=1e-9`) `dKE_dnu` on 2, 4 and 8 ranks is `2.9e-3`, `3.3e-3` and `3.3e-3` from serial, and the kinetic energy `2.6e-5`, `3.2e-5` and `3.2e-5`: the one-sided convection stencil at the rank faces, about the same absolute change in both (the derivative is small, `ν dKE/dν` is 2.6 % of the kinetic energy). At the default tolerance (`Float32` or `Float64`) the same comparison gives `4e-2` in the last record and `1e-4` in the four before it, which is the tolerance effect of the first point, not MPI.

### Halo timers and memory

`--laps` times the phases of every halo of WaterLily's own exchange during the timed steps, with a copy of its routine (`_exchange!` of `WaterLilyMPIExt`, `mpi-igg` since `57443f8`; `mpi/fused/halo_diag.jl` does the same for branch `mpi-igg-fused`). Rank 0 prints, per array, the calls per step and the median over the ranks of the mean time per call of `wait` (the kernels launched before the halo), `pack`, `post` (the receives and sends), `work` (the loop that overlaps the messages), `wait_recv`, `unpack` and `wait_send`, then one line with their sums in ms per step, where `halo` is all of them but `wait` and `work`:

```
[ Info: HALO  calls=52.0  wait=...  pack=...  post=...  work=...  wait_recv=...  unpack=...  wait_send=...  halo=...ms  sync=1
```

The run synchronizes the backend around the pack, the overlapped loop and the unpack, so that each phase holds its own GPU time (the routine itself synchronizes once, after the pack, and does not wait for the unpack). So a run with `--laps` is not the timing of the step: the halo share is `halo` over the time per step of the same run. `wait_recv` also holds the time a rank waits for a slower neighbour to reach its sends. `LAPS_SYNC=0` leaves the routine's single synchronization, and `pack` then includes the wait for the kernels launched before the halo, as in the laps of `mpi/fused/halo_diag.jl`.

The `MEMORY` line gives the bytes of the arrays of the simulation per interior cell of the rank's block (the ghost cells are in the bytes, so the figure falls slightly with the size) and those of the halo plans (index lists and buffers). In 3D `Float32` the arrays take 151.8 B per interior cell at `32^3`, 138.0 at `64^3` and 131.5 at `128^3` (about 126 B per cell of the padded block: 26 fields of the flow, 4 more of the top multigrid level, and 9 per coarser level). A `Dual` with `N` partials takes `N + 1` times that, exactly: 262.9 B per cell with one partial and 657.2 with four at `128^3`.

### JUPITER jobs

`mpi/jobs/jupiter_ad.sh` runs, at every point, `Float32`, `Dual` (`AD_PARTIALS`, default 1) and `Float32` again back to back in one allocation and at one WaterLily commit (the two `Float32` runs give the scatter of the ratio; between allocations the same point has varied by 20 %), then both with `--laps`; then, last, so that a time limit cuts them first, both at the weak points with a pressure tolerance that converges the derivative (`AD_TOL`, default `2e-6`), more partials (`AD_MORE_PARTIALS`, default 4 up to 2 nodes) and every eltype with device-to-device halos (`AD_DEVICE`, on up to 2 nodes). Each argument is a set of points, `"MODE LOG2P NP [NP ...]"`; without arguments a job on one node runs `"weak 7 1" "weak 8 1 4"` (one GPU at `128^3` and `256^3`, 4 GPUs at `256^3` each) and a job on `N` nodes `"weak 8 4N" "strong 9 4N"`. `mpi/jobs/jupiter_ad_check.sh` (2 nodes) is the correctness check: AD on 8 GPUs against AD on one GPU with converged solves, AD against finite differences on 8 GPUs for three ε, and, at the settings of the timed runs, AD on 1, 4 and 8 GPUs against one GPU without MPI, device-to-device against staged halos, the values against a `Float32` run and 8 CPU ranks.

```sh
sbatch -A <budget> --reservation=develbooster mpi/jobs/jupiter_ad_check.sh     # 2 nodes: correctness, 16 runs, about 20 min
sbatch -A <budget> --reservation=develbooster -N 1 mpi/jobs/jupiter_ad.sh      # 1 and 4 GPUs, 23 runs, about 30 min
sbatch -A <budget> --reservation=develbooster -N 2 mpi/jobs/jupiter_ad.sh      # 8 GPUs, 18 runs, about 25 min
sbatch -A <budget> -N 8 --time=00:40:00 mpi/jobs/jupiter_ad.sh                 # 32 GPUs
sbatch -A <budget> -N 16 --time=00:40:00 mpi/jobs/jupiter_ad.sh                # 64 GPUs
julia mpi/collect.jl --out=data/mpi/jupiter_ad.csv data/mpi/jupiter_ad_*       # one row per run of all the jobs
```

The time estimates take 1.2 to 1.5 min per run, what the earlier jobs took; each run has a limit of its own (`RUN_MINUTES`, default 10, passed to `srun --time`), so that one that hangs does not take the rest of the job with it, and the jobs ask for 1 h (`jupiter_ad.sh`) and 40 min (`jupiter_ad_check.sh`) unless `--time` says otherwise. Every run writes its whole output to `data/mpi/jupiter_ad_<job>/<point>_<run>.txt`, and the job prints the table of its runs and writes `runs.csv` there. `mpi/collect.jl` reads everything from what the runs printed, not from file names: the commits, the eltype and its partials, the ranks, the mode and the sizes, the time per step, the mean Poisson iterations, the pressure tolerance when set, the transport (`gpu_aware`), the halo phases of a run with `--laps` and the memory. `ms_ratio` and `mem_ratio` relate a run with partials to the mean of the `Float32` runs of the same job and point, and `iters_differ` flags a pair whose Poisson iterations differ (the ratio then holds another amount of work). It also reads the job outputs of `mpi/jobs/submit.sh`, several runs per file. The check job writes to `data/mpi/jupiter_adcheck_<job>/`, with its tables in `summary.txt`; its runs have no warm-up, so they are no timings.
